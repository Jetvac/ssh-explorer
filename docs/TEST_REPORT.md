# Реально выполненные проверки

> Результаты этого отчёта относятся к испытаниям 0.1.0. Текущая приёмка 0.2.0-beta.1, новые сценарии и открытые пункты собраны в [ACCEPTANCE.md](../ACCEPTANCE.md), [PROFILE_CRASH](PROFILE_CRASH.md) и [UI_PARITY](UI_PARITY.md).

03.11.2026, Windows x64, локальный .NET SDK 10.0.403.

## Автоматические проверки модулей

`tests/SSHExplorer.Tests` — самостоятельный консольный test runner, без имитации успеха сетевых сценариев. Release-сборка: 0 ошибок, 0 предупреждений. Выполнено **34 модульных теста, 34 пройдено, 0 ошибок**.

- `/proc/stat`: исключение двойного учёта guest, число CPU, переполнение.
- `/proc/PID/stat`: имя со скобками, пробелами, переводом строки и shell-метасимволами.
- Base64-рамка протокола сохраняет NUL/переводы строк; неполный, дублирующийся и чрезмерный ответ отклоняется.
- Память: MemAvailable, KiB, явно подписанная оценка при отсутствии MemAvailable; недоступное не превращается в ноль.
- CPU и скорости: первый замер недоступен, затем вычисление разности; PID reuse, исчезновение в середине замера, reboot и сброс счётчиков.
- Чтение/запись процессов отделены от сети интерфейсов. История ограничена; параллельных запросов нет.
- Сигналы: защита PID 1, неизвестного UID, изменённой идентичности и запрещённых номеров сигнала. Автоматический sudo отсутствует.
- POSIX: case-sensitive пути, обратный слеш, UTF-8 и shell-кавычки; запрет NUL и недопустимых имён.
- Проверка привязок native SFTP к закреплённой версии SSH.NET 2026.0.0.
- Безопасные имена Windows и запрет выхода из выбранного каталога скачивания.
- Trust store: отмена, временное доверие одной сессии, сохранение и restart, endpoint/port/algorithm, блокировка изменённого ключа до обычного диалога, объединение одновременных запросов.
- Временное доверие: изменение ключа или алгоритма внутри той же логической сессии блокируется до обычного trust-диалога; новая логическая сессия не наследует временное доверие.
- Профили и настройки: два профиля, атомарная перезапись и резервная копия.
- Windows DPAPI CurrentUser: успешный roundtrip, отсутствие открытого секрета во всех файлах тестового store, удаление секрета.
- Владение сессиями: независимые lifetime, повторное закрытие одной не отменяет другую.

Команды запуска из корня репозитория:


## Запуск интеграционных сценариев

`--linux-integration <isolated-config.json>` принимает только явно заданный стенд и независимо полученный SHA256 host key. Пример: `tests/SSHExplorer.Tests/linux-integration.example.json`. Пароль/ключ — свежие тестовые; `SecretFile` позволяет не передавать секрет в командной строке. Поддерживаются пароль и приватный ключ с passphrase.

Режим проверяет реальные host trust и вход, SFTP CRUD и опасные имена, потоковый upload/download SHA256+progress, безопасную отмену переименования, отказ при внешнем изменении той же длины с сохранённым mtime, copy/move/descendant guard, конфликты skip/keep-both/replace, merge каталогов, отмену замены с сохранением оригинала, chmod/chown в пределах полномочий, symlink/broken/cycle без удаления цели, несовместимые Windows-имена и коллизии регистра, независимые сессии, настоящий `/proc`, независимое измерение памяти/CPU и защиту PID identity. `RunDirectoryLoad=true` включает каталог 10 000 объектов.

Нагрузочная проверка файла >2 ГиБ включается явным `LargeFileBytes` >2147483648. Значение 0 не объявляет такую проверку выполненной.

Дополнительные узкие режимы не повторяют весь модульный набор:

```powershell
.\.tools\dotnet\dotnet.exe tests\SSHExplorer.Tests\bin\Release\net10.0\SSHExplorer.Tests.dll --linux-capabilities isolated-config.json
.\.tools\dotnet\dotnet.exe tests\SSHExplorer.Tests\bin\Release\net10.0\SSHExplorer.Tests.dll --network-failure isolated-proxy-config.json
```

`--network-failure` содержит собственный тестовый TCP proxy только на loopback, с явно заданным `ProxyPort` и `DelayMilliseconds`; пример — `tests/SSHExplorer.Tests/network-failure.example.json`. В основное приложение proxy не включён. На Linux ничего для него не устанавливается; серверный SSH и параллельные соединения приложения не затрагиваются.

## Выполненная реальная Linux-интеграция

Изолированный QEMU-стенд: Alpine Linux 3.24.3, ядро 6.18, OpenSSH 10.3, обычная свежая учётная запись `sshx-test`, ext4. Python и htop на сервере отсутствуют. Подготовка этого стенда — отдельная разработческая работа; приложение его не разворачивает и не устанавливает ничего на управляемые серверы.

Первый прогон обнаружил реальный дефект: сериализация полученных SFTP-атрибутов возвращала только изменённые поля и давала ложный mode 0000. При копировании/замене это снимало права с итогового файла. Исправлено извлечением всех 12 публичных permission flags; повторная проверка выполнена с чистым тестовым каталогом.

Базовый реальный набор содержит **16 сценариев**. Парольный прогон завершился **49/49** (на тот момент 33 модульных +16 реальных), [лог](test-results/linux-password.log). Позднее модульный набор расширен до 34. Успешно проверены перечисленные CRUD/transfer/link/name/undo-сценарии, настоящие SSH/SFTP, реальный `/proc`, сравнение MemTotal и MemAvailable с отдельным чтением `/proc/meminfo`, блокировка SIGTERM при несовпадении starttime. Объекты создавались только в отдельном `sshx-integration-<id>` внутри тестового home; каталог удалён проверенным SFTP cleanup.

Прогон с **зашифрованным приватным Ed25519-ключом и passphrase**: **52/52** — 34 модульных +16 базовых +2 дополнительных реальных сценария, [лог](test-results/linux-encrypted-key-and-10000.log). Дополнительно успешно отправлены SIGTERM и SIGKILL двум специально созданным PTY-процессам `sleep` с проверкой их идентичности и фактического завершения. Никакие посторонние процессы для проверки сигналов не использовались.

Реальный каталог **10 000 элементов** создан отдельными ограниченными командами в тестовом каталоге и прочитан SFTP: точное количество и уникальные имена подтверждены; перечисление заняло **0,75 с**, рабочий набор тестового процесса **89 МиБ**. Затем выполнено безопасное удаление только тестового дерева. Это проверяет backend; отзывчивость UI при показе 10 000 строк проверяется отдельно.

Независимое сравнение CPU — отдельный дополнительный сценарий: по двум SSH-соединениям в выровненных приблизительно 3-секундных интервалах получены **монитор 96,93%, независимая выборка 96,67%**, разница **0,26 процентного пункта**. Шкала обоих измерений — 0–100% всех видимых CPU; guest не добавляется повторно. Прогон **52/52** включал 34 модульных, 16 базовых, уже проверенные сигналы и новую CPU-проверку; [лог](test-results/linux-cpu-comparison.log).

Большой файл **2 148 532 224 байт** (>2 ГиБ) успешно загружен и скачан обратно с совпадением SHA256: `F9C8466CDAC8F598A9DBBE999B62B47C2745C7B7368CD6BFCEE1B636368A9071`. ## Обрыв сети, задержка, отмена и повтор

Изолированный тестовый proxy `127.0.0.1:22226 → 127.0.0.1:22222` добавлял **50 мс задержки каждому пересылаемому блоку в обоих направлениях**. Это воспроизводимая искусственная задержка, не заявление о точном измеренном RTT. Весь основной SSH-сервис и другие соединения VM продолжали работать.

**6/6 реальных сетевых сценариев пройдено**, [лог](test-results/linux-network-failure.log):

1. Upload 4 МиБ оборван после **524 288 байт** закрытием только принадлежащих proxy соединений. Задание перешло в `Failed`; SHA256 существующего корректного удалённого файла и локального источника сохранились.
2. Восстановление proxy не создало новых соединений, не возобновило задание и не перезаписало оригинал.
3. Явная новая передача в свежей проверенной SSH-сессии заново запросила разрешение конфликта (один подтверждённый конфликт), передала **4 194 304 байта** и совпала по SHA256. Старое задание осталось `Failed`.
4. Отмена медленного SSH exec завершила локальное ожидание за **388 мс**.
5. Закрытие сессии с действительно незавершённым запросом отменило его и освободило все принадлежащие ей транспорты за **404 мс**; активных proxy-соединений осталось **0**.
6. Удалён только выделенный тестовый каталог; независимое прямое SSH-подключение к основному серверу оставалось работоспособным.

Proxy завершён вместе с тестовым процессом. Дополнительная проверка Windows TCP inventory подтвердила: слушателей на порту **22226 нет**. VM и основной порт 22222 оставлены для дальнейшей проверки опубликованного UI.

## Границы этого отчёта

Числа успешных прогонов выше **не складываются**: общие сценарии выполнялись с разными способами аутентификации и параметрами нагрузки. Отдельно подтверждены 34 модульных проверки, 16 базовых реальных сценариев и явно перечисленные дополнительные риски.

Windows UI, Explorer drag-and-drop, матрица DPI/тем, отзывчивость отображения 10 000 строк и чистая автономная Windows не проверяются этим backend runner и не считаются пройденными по его результатам. Их фактический итог отражается отдельно главным агентом в ACCEPTANCE.md. Измерение RSS относится к консольному тестовому процессу, а не к суммарной памяти GUI/WebView2; тест не заявляет измерение всей памяти опубликованного приложения.

## Мониторинг: технические границы

Коллектор не устанавливает ничего на сервер. Использует существующие `/bin/sh`, `dd`, `base64`, `tr`, опционально `getconf` и `df`; отсутствие необходимых утилит сообщает как ограничение. Фиксированное ограничение процесса: до 2048 PID по умолчанию, максимум 4096; cmdline до 4096 байт; общий ответ до 16 МиБ. Опрос запускает UI только для активного видимого монитора и не ставит следующий запрос поверх незавершённого.

CPU процесса — доля суммарных видимых CPU 0–100%; сеть измеряется по интерфейсам, не PID. Наблюдаемая область подписана как доступное пространство имён хоста/контейнера. SIGTERM/SIGKILL повторно проверяют PID/starttime/UID перед kill; остаточная гонка между проверкой и сигналом остаётся, атомарность pidfd не заявляется.

Семантика счётчиков проверена по [документации ядра Linux](https://docs.kernel.org/filesystems/proc.html), [proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html) и [proc_stat(5)](https://man7.org/linux/man-pages/man5/proc_stat.5.html).
