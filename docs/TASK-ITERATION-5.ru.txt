# SSH Explorer после beta.3: привычное поведение Проводника и доводка Windows 11 UI

Продолжай разработку существующего SSH Explorer. Следующая итерация должна приблизить приложение к Windows 11 через законченные пользовательские действия, согласованные контролы и сравнение с нативными референсами. Реализуй изменения, проверь их разрешёнными средствами и сохрани результат в GitHub.

**Репозиторий:** [Jetvac/ssh-explorer](https://github.com/Jetvac/ssh-explorer).  
**Baseline:** `v0.2.0-beta.3`, commit `e8ef6815dd3417dcbda632077ed8408c77576d04`.

## 1. Сохрани достигнутое и уточни цель

Пользователь оценил beta.3 как улучшение, но интерфейс ещё не принят. Сохрани новую композицию мониторинга, закреплённые разделы, отдельную прокрутку дерева, полноценную заливку метрических ячеек, состояния данных, временную шкалу графиков и отмену скрытого сбора.

Существуют роли стилей, `UiMotion`, CI-галерея разных экранов, проверки геометрии, защищённого входа и выпуска. Изучи актуальный HEAD, рабочее дерево, `UI_PARITY`, `UI_COMPOSITION_BETA3`, `CI_BETA3` и `ACCEPTANCE`. Не реализовывай уже сделанное заново.

Успешный пользовательский запуск относится к beta.2; текущая оценка beta.3 относится к представленным изображениям. Причина прежнего парольного crash остаётся неизвестной. Сохрани защитные изменения и регрессии. При повторении вылета он вновь получает первый приоритет; текущую UI-итерацию не превращай в повтор всего прежнего расследования.

Базовые требования неизменны: Windows EXE-комплект с включёнными зависимостями; существующая WPF/.NET-архитектура; Linux через SSH/SFTP без установки чего-либо на управляемый сервер; доверенные host keys; независимые закрываемые серверные вкладки; терминал, мониторинг, файловое дерево, preview и передача файлов.

**Основной приоритет этой итерации — файловые сценарии и общие компоненты.** Мониторинг требует адресной доводки, описанной ниже.

## 2. Сравнивай с Windows 11 и учитывай границы изображений

Используй тройку: **Windows-референс → beta.3 → новый результат**. Before/after собственной программы полезен, но сам по себе не устанавливает сходство с Windows.

Для каждой правки укажи наблюдаемое расхождение, целевое поведение/оформление и доказательство. Используй исходные референсы Explorer/Task Manager пользователя. Для полей ввода и списков дополнительно сверяйся с официальными образцами Windows/Fluent. Не подменяй настольный интерфейс веб-оформлением.

Сохрани имеющуюся CI-галерею и расширяй её недостающими состояниями. В beta.3 уже есть файловый экран, Home, меню видов, форма сервера, разные размеры мониторинга и другие сцены.

Правильно интерпретируй текущие изображения:

- Чёрная/прозрачная зона справа сверху исключена из `RenderTargetBitmap` вместе с native caption/DWM; это не установленный дефект окна.
- Буква `S` в состоянии процесса приходит из ручных данных fixture; реальный `ProcParser` переводит её в «Ожидание».
- Десятичная точка может отражать культуру CI runner.
- Окно сравнения не активировано, поэтому серое выделение не доказывает неправильное active selection.
- Перед сравнительным кадром сортировка очищается: отсутствие стрелки на нём не доказывает отсутствие сортировки.

Не исправляй продукт вслепую по этим особенностям. Сделай тестовые сцены представительными и явно фиксируй их состояние.

Если доступны субагенты, параллельно используй анализ Windows-референсов, реализацию WPF и независимую проверку. Общие файлы должны иметь одного владельца. Проверяющий оценивает фактические кадры и поведение, а не только перечень изменённых свойств.

## 3. Переименование и создание непосредственно в списке

В beta.3 `FileBrowserView.Rename` и `Create` открывают `Ui.Prompt`. Переведи основной сценарий на редактирование имени в строке или плитке.

### Переименование

F2 и соответствующая команда меню включают редактор выбранного объекта на его месте. У обычного файла первоначально выделяется базовая часть имени; расширение остаётся доступным для редактирования. Для папок и dotfiles задай предсказуемое правило, не превращающее `.bashrc` в пустое имя.

Enter подтверждает операцию, Esc отменяет введённое изменение. Ошибка имени, конфликт или отказ сервера позволяют исправить значение без повторного запуска действия и потери ввода. Во время выполнения обозначай реальную занятость; повторный Enter не создаёт вторую операцию.

Сохрани идентичность редактируемого объекта. Сортировка, refresh и виртуализация не должны переносить редактор на другую строку. После успеха сохраняются выбор, видимость объекта и понятный клавиатурный фокус.

### Создание

«Создать папку» и Ctrl+Shift+N должны приводить к новой папке с редактируемым именем непосредственно в текущем представлении. Аналогично согласуй создание пустого файла.

Следуй понятному контракту, близкому Explorer: сначала подтверждённое сервером создание с уникальным предлагаемым именем, затем редактирование имени. Esc после успешного создания оставляет созданный объект под его текущим именем. При ошибке создания не показывай фиктивный успешно созданный объект. Состояние до подтверждения сервером должно отличаться от обычной папки.

Конкурентное появление такого же имени на сервере обрабатывай корректно. Не перезаписывай существующий объект ради удобного поведения.

Для удалённых имён используй поддерживаемые правила POSIX. Не навязывай все ограничения имён Windows Linux-серверу. Сохрани безопасные SFTP-операции, корректную работу с Unicode, пробелами и кавычками.

Проверь таблицу и плиточные виды, отмену, конфликт, задержку ответа и повторное нажатие. Глобальные Delete/Enter/Copy не должны выполнять файловую команду, когда пользователь редактирует текст имени.

## 4. Адресная строка и выделение

### Исправление ошибочного пути

В beta.3 Enter после `NavigateAsync` всегда скрывает редактор адреса; повторное открытие подставляет последний успешный `CurrentPath`. Из-за этого ошибочно набранный путь неудобно исправлять.

Раздели успешный переход, отказ и отмену:

- При ошибке оставляй введённый путь редактируемым и показывай краткую причину.
- Enter повторяет попытку с исправленным значением.
- Esc возвращает последний успешно открытый каталог.
- Успешный переход возвращает breadcrumbs.
- История, содержимое и текущая папка фиксируются только после успешного актуального запроса.

Проверь `LostKeyboardFocus`: показ сообщения или работа с соседним контролом не должны неожиданно уничтожать введённый адрес. Сохрани generation/cancellation guards и защиту от позднего ответа старой навигации.

### Выделение объектов

Согласуй single-click, Ctrl/Shift, снятие выбора и прямоугольное выделение в Details и плиточных видах.

Текущий `ConfigureLasso` подключён к `tiles` и перебирает реализованные контейнеры. Доведи сценарий для Details и прокрутки: выделение рамкой начинается на свободной области, перетаскивание выбранных файлов — на объектах. Эти жесты не должны мешать друг другу.

Обеспечь контролируемую прокрутку у края и корректный набор выбранных объектов при виртуализации. Не создавай визуальные контейнеры всего каталога ради расчёта выделения. Esc, потеря capture, смена раздела и закрытие вкладки очищают рамку и таймеры.

Сохрани уже сделанное поведение правого клика по выбранной группе. Контекстное меню должно работать с этой группой, а не с устаревшим выделением другого представления.

## 5. Панели команд и контекстные меню

### Адаптивная панель

В файловом экране и Home остаётся `WrapPanel`. Задай явную политику приоритетов и overflow.

При обычном уменьшении ширины сохраняй один основной ряд команд; второстепенные действия перемещай в «…». У адреса, поиска и команд должны быть согласованные минимальные размеры. Не допускай случайного второго или третьего ряда, изменяющего высоту рабочей области. При большом масштабе текста допускается только заранее продуманная доступная перекомпоновка.

Проверь доступность скрытых команд с клавиатуры, порядок фокуса, tooltip, disabled state и одинаковое действие команды в панели и overflow. Используй подходы уже реализованной адаптивности мониторинга, не создавая несвязанный набор правил.

### Контекстное меню

Сопоставь композицию меню с предоставленным Windows 11-референсом: компактная группа основных действий, ясные разделители, согласованные иконки, размеры и отступы. Сохрани Esc, подменю, клавиатурную навигацию, доступные имена и возврат фокуса.

Исправь подтверждённые границы beta.3:

- «Вставить» учитывает применимый clipboard, целевую папку и доступность сессии.
- «Отменить» учитывает реально доступную поддерживаемую операцию и понятно называет её.
- «Закрепить / открепить» заменяется конкретным действием по текущему состоянию.
- Каждый режим «Просмотреть» имеет подходящую смысловую иконку вместо одного общего значка для всех восьми режимов.

Учитывай вид объекта, количество выбранных элементов и фактический источник вызова меню. Проверка доступности команды не должна запускать тяжёлую сетевую операцию при открытии меню.

Сохрани честную семантику удалённых операций: не обещай корзину Windows или восстановление удаления, если этого нет. Ошибка передачи и отмена не должны приводить к преждевременному удалению исходника.

## 6. Доведи реальные контролы и диалоги

В CI-галерее форма сервера ещё сочетает разные рисунки полей: выпадающий список, текстовый и парольный ввод, checkbox и кнопки. Проверь фактически применяемые `ControlTemplate`, наследование и возможный fallback темы. Наличие Fluent-словаря и успешный seal стилей не доказывают нужный внешний вид.

Согласуй по Windows-референсам:

- фон, обводку, радиус и высоту контролов;
- текст, baseline и расстояние от label до поля;
- normal/hover/pressed/focused/disabled/error states;
- открытый ComboBox, его пункты, скроллирование и клавиатурный выбор;
- checkbox и переключение показа пароля;
- primary/secondary buttons и footer диалога.

Используй одну систему для профиля сервера, Credentials, Trust, Interactive, настроек, свойств, конфликтов передачи и очереди. Сохрани владельца окна, отмену, жизненный цикл и уже исправленный ввод секретов.

Сократи длинные служебные объяснения на основной поверхности, сохранив понятные различия «Сохранить» и «Сохранить и подключиться», условия сохранения пароля и важные ошибки. Дополнительные сведения доступны по запросу. Не делай элементы только визуальными: нормальная работа клавиатуры и средств доступности обязательна.

Проверь нормальное состояние, заполненную форму, ошибку, открытый список, длинные строки и маленькое окно. Не меняй способ аутентификации или хранение секретов ради оформления.

## 7. Вкладки при нескольких серверах

Проверь не только два коротких заголовка. В текущем `SessionTabControl` горизонтальная полоса скрыта, вкладки имеют минимальную ширину, а tooltip заголовка содержит endpoint без полного пользовательского имени.

Доведи случай нескольких серверов:

- Активная вкладка и её кнопка закрытия доступны.
- Полное пользовательское имя можно узнать по запросу.
- Скрытые вкладки доступны мышью и клавиатурой через понятную прокрутку/overflow.
- Длинные названия, одинаковые имена разных сессий и изменение ширины не ломают компоновку.
- Закрытие выбирает предсказуемую соседнюю вкладку и освобождает только свою сессию.
- Hover-переключение во время файлового drag не меняет исходный сервер и payload.

Сохрани drag reorder, если он реализован. Не смешивай жест перемещения вкладки с перетаскиванием файлов на вкладку. Горячие клавиши учитывают фокус редактора имени, адресной строки и терминала; терминальный ввод не перехватывается произвольными глобальными shortcuts.

## 8. Адресная доводка мониторинга

Сохрани композицию beta.3 и исправленные графики. Следующие задачи относятся к устойчивости обычной работы.

### Команды и фоновый сбор

`MonitorViewModel.CanSignalSelected` зависит от `!IsBusy`, а каждый `Poll` переключает `IsBusy`. Проверь поведение при долгом замере: обычный фоновый сбор не должен постоянно мешать пользователю выполнить допустимое действие над выбранным процессом.

Раздели фоновое обновление, устаревшие данные и собственную выполняемую команду. Не исправляй это простым удалением защитного условия: повторная проверка identity, состояния и прав непосредственно перед сигналом сохраняется. Процесс, завершившийся или сменивший identity, не получает действие по старому PID.

### Сортировка и предпочтения

Проверь сортировку через заголовок и соответствующие команды, направление/индикатор, неизвестные значения и обновление метрик после сортировки. Сохрани выбранную идентичность и разумное положение списка.

Настройки колонок сейчас живут в `MonitorView`. Сохраняй пользовательские предпочтения видимости, порядка, ширины и сортировки после повторного открытия приложения. Различай предпочтение и временное адаптивное скрытие на узком окне. Поисковый фильтр и выбранный процесс остаются контекстом своей сессии.

### Форматирование

Раздели формат по роли: агрегатный процент в шапке, значение процесса, размер, скорость и время. По предоставленному Task Manager-референсу агрегаты можно показывать целыми процентами, а значения строк — с дробной частью. Это изменение отображения, не точности измерений.

Уважай региональные настройки. Не заменяй точки запятыми вручную. Для сравнимых CI-кадров явно фиксируй культуру и проверь `ru-RU`/`en-US`.

## 9. Представительные сцены и проверка по состояниям

Используй существующий CI-render pipeline. Его окно и данные должны представлять проверяемое состояние, а не случайный набор удобных строк.

Для мониторинга включи результаты обычных преобразований: «Выполняется», «Ожидание», длинное «Ожидание I/O», разные величины, неизвестные/устаревшие значения, сортировку и обновления. Для файлов — папки, несколько типов, длинные Unicode-имена, dotfiles, даты, размеры и ссылки. Реальные пользовательские данные не нужны.

Используй production formatters и модели состояний. Не меняй рабочие правила приложения специальным условием ради красивого render. Fixture остаётся явно обозначенным и не выдаётся за сетевую проверку.

Расширь галерею по изменённым границам:

| Сценарий | Что показать и проверить |
|---|---|
| F2 | Редактор в строке и плитке, расширение/dotfile, подтверждение и отмена |
| Ошибка имени/конфликт | Введённое имя сохранено, ошибку можно исправить |
| Новая папка | Реальное состояние создания, последующее имя и понятный Esc |
| Ошибочный путь | Адрес остаётся редактируемым; исправление, Enter и Esc работают |
| Выбор группы | Ctrl/Shift, рамка, прокрутка и сохранение группы при меню |
| Узкий файловый экран/Home | Предсказуемый overflow и доступность команд |
| Меню | Верные enabled states, различные иконки видов, клавиатурный выбор |
| Формы | Согласованные поля и открытый ComboBox, focus/error/disabled |
| Несколько вкладок | Длинные имена, доступ к скрытым вкладкам, закрытие и drag-over |
| Мониторинг | Команда при фоновом сборе, сортировка через заголовок, восстановление колонок |

Фиксируй commit/DLL, клиентский размер, DPI, масштаб текста, культуру, тему, active/inactive state, фокус, данные и состояние сортировки. Не сравнивай разные состояния и не называй результат pixel-perfect при неизвестном DPI нативного референса. Если условия исходного Windows-снимка неизвестны, сравнивай структуру и рисунок компонентов с явно ограниченной точностью.

Добавь active/inactive selection, keyboard focus и hover там, где среда действительно позволяет их получить. Программная установка состояния или события имеет отдельный статус от физического ввода.

Новые тесты должны проверять изменённые границы: операция выполняется один раз, ошибка сохраняет ввод, объект не подменён сортировкой, отмена очищает capture, видимость команды согласована с действием. Не увеличивай счётчик assertions повторением setters.

Существующие 34 проверки и галерея beta.3 сохраняются. Они не становятся 34 полными пользовательскими маршрутами.

## 10. Motion, DnD и текущие разрешения

Сохрани `UiMotion`, системное отключение, High Contrast, прерывание и cleanup. Доработки inline-редактирования, меню и overflow не должны вызывать скачки layout, мерцание или отложенные команды после ухода с экрана. Не добавляй эффекты ради количества. WebView2/HWND терминала сохраняет специальную обработку.

Особенно проверь взаимодействие нового выделения/редактирования с существующим DnD: начало drag, hit testing, source identity, Copy/Move/None, drop в дерево и вкладку, Escape и закрытие участвующей сессии. Сохрани Windows ↔ сервер, A ↔ B и операции внутри сервера. Не переписывай native COM без выявленной причины.

В beta.3 зафиксирован действующий запрет Computer Use на пользовательском рабочем столе. Сохраняй его. Разрешены код, сборка, headless-проверки и WPF HWND/layout/render в Windows GitHub Actions. Не используй прежнее временное разрешение beta.2 как действующее.

Физический ввод, настоящий Explorer gesture, native caption/Snap, motion video, реальная полная DPI/High Contrast-матрица и чистая Windows остаются отдельными проверками. Подготовь сценарии, сохрани точные статусы и продолжай доступную работу без повторного запроса разрешений на код/CI.

`RenderTargetBitmap` не доказывает DWM, фактический захват мыши или видимую плавность. Clock tests проверяют механизм переходов, но не пользовательское ощущение движения.

## 11. GitHub, релиз и результат итерации

Сохрани незакоммиченные изменения пользователя. Делай законченные коммиты по связанным задачам и регулярно push в принятый рабочий процесс репозитория. Приоритет: файловые сценарии → общие контролы/меню/overflow → адресные улучшения вкладок и мониторинга → проверка и выпуск.

Обнови README, CHANGELOG, текущий ACCEPTANCE и UI_PARITY. Исправь устаревшее название версии в актуальной сводке. Исторические отчёты и уже подтверждённую проверку beta.3 сохрани с их настоящими commit и датами.

Следующий выпуск — новая свободная beta, например `0.2.0-beta.4` после проверки tags. Версия, commit, CI, tag, комплект, SHA256 и финальные render evidence должны соответствовать одному результату. Подготовь и опубликуй выпуск в рамках ранее разрешённой работы с GitHub. Не перезаписывай beta.3.

Сохрани self-contained EXE-комплект, host trust, точность пароля, отложенную запись секрета, отмену подключения, обычный auth-маршрут, терминал и файловые регрессии. Повторяй дорогие прогоны по риску изменения, не ради количества.

Результат этой итерации:

1. Привычное редактирование имени и создание объектов в файловом представлении.
2. Исправление ошибочного адреса без потери ввода.
3. Согласованные выделение, DnD, команды и контекстные меню.
4. Адаптивные Files/Home и доведённые реальные контролы диалогов.
5. Удобные несколько вкладок и адресные улучшения мониторинга.
6. Сравнимые доказательства по состояниям, сохранённый CI и новый проверяемый выпуск.

В итоговом отчёте сначала покажи, что пользователь теперь делает удобнее, и реальные изменённые экраны. Затем дай ссылки на commit, CI, релиз и оставшуюся приёмку. Разделяй реализованное, проверенное и недоступное для живой проверки.

**Визуальная приёмка остаётся за пользователем.** Не объявляй интерфейс принятым из-за зелёного CI. Выполни согласованный объём этой итерации самостоятельно и не заканчивай вместо реализации вопросом, продолжать ли работу.
