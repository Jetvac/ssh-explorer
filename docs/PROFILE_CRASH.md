# Профили: два отдельных случая падения

## Открытый парольный случай — расследование beta.2, 03.11.2026

**Статус: BLOCKED для живого воспроизведения; причина актуального парольного crash не установлена.** Пользователь уточнил: после «Подключиться», до диалога доверия. Действует указание «Продолжайте код и CI, окна позже»; новые EXE и окна на рабочем столе в этой итерации не запускались. Предыдущее исправление SelectionChanged не засчитывается как доказательство устранения этого сообщения.

Read-only проверка Windows Application Error обнаружила два последних доступных события в 15:34:16 и 15:34:52 МСК: **AppVersion 0.1.0.0, exception 0xC00000FD**, faulting module `coreclr.dll` / `unknown`. Файлы, сейчас находящиеся по указанным в событиях путям, имеют старые SHA из исторического случая ниже. Это доказывает версию в этих событиях и соответствие текущих файлов старой поставке; хеши не получены из памяти аварийного процесса. Это не воспроизведение beta.1 и не доказательство причины любого другого вылета. [Обезличенные метаданные](test-results/beta2-os-crash-provenance.json) не содержат пользовательских путей, настроек или dumps.

Точный скачанный опубликованный beta.1 отличается: EXE SHA `2cf2549a6984c1e31997cdb878d9198faf0b46d88b7426f378b6a00c6de206e3`, App DLL SHA `8c422880599b84239902d48c5a9152f9672c0caa26ea6465f80d8964b09556cb`, ProductVersion `0.2.0-beta.1+eda137a734e8fc259eb97fca300b2072d11232a8`. Комплект статически проверен; его EXE не запускался. Совместимость store проверена через опубликованный Core на отдельной копии: [профильный отчёт](PROFILE_FLOW_BETA2.md).

В beta.2 устранены отдельно проверенные дефекты и закрыты границы:

- Save-and-connect передаёт точный пароль в памяти, без Trim; запись нового DPAPI-секрета отложена до успешного подключения. Неверная или устаревшая попытка сохраняет прежний секрет.
- Реестр попыток блокирует повторные команды одного профиля до первого await; явная независимая сессия разрешена. У каждой операции GUID, owner cancellation и сетевой timeout.
- Credentials/Trust/Interactive выполняются у владельца на UI-потоке; очередь сериализуется на сессию, отменённые запросы не показываются позже. Все дополнительные SSH каналы используют тот же договор, с отдельными operation IDs.
- Исправлена гонка раннего Dispose во время vendor Connect: логическая отмена немедленна, физический транспорт освобождается после unwind SSH.NET. Она подтверждена сетевым тестом, но не объявлена причиной пользовательского crash.
- Создание файлового вида и первая навигация имеют отдельные стадии. При ошибке папки остаётся явный путь восстановления через Home/root. Терминал/WebView2 и монитор создаются при открытии раздела.
- Недоступный или повреждённый защищённый секрет предлагает повторный ввод без удаления профиля. Ожидаемый отказ чтения секрета после открытия формы сохраняет введённые поля.

Диагностика JSONL содержит build/commit, runtime/OS, process ID, operation/session/parent ID, стадию и результат, exception type/HRESULT и методы стека. Сохранение профиля, чтение секрета, credentials, transport/trust/auth/exec/SFTP, view construction, initial navigation и terminal initialization различимы. Сообщения исключений, поля профиля, пароли/passphrase/OTP, команды и ответы сервера не пишутся. Ротация — текущий файл около 1 МиБ и одна предыдущая копия. Пограничные записи ожидаются и сбрасываются на диск; fatal handlers используют синхронную запись с ограниченным ожиданием и запасным файлом. Unknown Dispatcher exception больше не подавляется безусловным Handled=true. App exit/ProcessExit и сбой WebView2 отмечаются отдельно. Managed handlers не гарантируют запись при StackOverflow, native crash, kill или потере питания.

Проверки и их границы: [AUTH_NETWORK](AUTH_NETWORK.md), [PROFILE_FLOW_BETA2](PROFILE_FLOW_BETA2.md), [13 headless проверок операций/приватности/передач](test-results/beta2-connection-headless.log), [приёмка](../ACCEPTANCE.md). Присваивание PasswordBox и RaiseEvent в CI не являются физическим вводом и запуском опубликованного EXE.

Для последующего разрешённого воспроизведения: распаковать новую версионную папку целиком; сверить версию в заголовке/параметрах и `build-info.json`; использовать отдельный store либо безопасную копию. Если вылет повторится, достаточно последних строк `Logs/diagnostics.log` из каталога настроек и времени/кода Windows Application Error. Путь журналов можно скопировать в параметрах. Не нужны пароль, адрес, полный settings.json, приватный ключ или memory dump. Публично передавать только обезличенные строки; каталог профилей целиком не отправлять.

## Исторический подтверждённый случай 0.1.0 → beta.1

03.11.2026. Исходная пользовательская поставка — **0.1.0**, Windows 11 x64 build 26200, .NET 10.0.14. Исходники этой поставки импортированы в Git как baseline `f15c2cd`; это идентификатор импортированного исходного состояния, а не встроенный commit старого EXE.

## Установленная причина

Само открытие `Dialogs.Profile` и сохранение корректно заполненной формы возвращали профиль без исключения. Отдельная проверка только этой формы поэтому не обнаруживала дефект.

Падение происходило в главном окне при выборе строки сохранённого сервера и последующем обновлении списка с выделением. WPF `SelectionChanged` является маршрутизируемым событием. Обработчик `TabControl.SelectionChanged` принимал также событие дочерней `DataGrid`, поскольку не проверял `OriginalSource`.

Получался синхронный цикл:

```text
Выбор строки DataGrid
  → всплывающий SelectionChanged попадает в обработчик TabControl
  → MainWindow.RefreshHome
  → HomeViewModel.Refresh / Rebuild
  → новый VisibleProfiles и восстановление SelectedProfile
  → DataGrid меняет выделение
  → снова обработчик TabControl
```

Результат — **фатальное переполнение стека**, код завершения `-1073741571` / `0xC00000FD`. Обычный `try/catch` вокруг сохранения или глобальный обработчик WPF не исправляет такую рекурсию. Inner exception отсутствует: это не цепочка перехватываемых managed exceptions.

Исправление в `MainWindow`:

- Обработчик вкладок принимает только `ReferenceEquals(e.OriginalSource, tabs)`.
- `RefreshHome` защищён от повторного входа через `try/finally`, без подавления исключений.
- Настоящее переключение вкладок продолжает обновлять состояние; выделение в дочерней таблице больше не запускает перестроение всех профилей.

## Доказательство на исходной поставке

Проверялся не только новый код. STA-проба ссылалась непосредственно на опубликованные DLL, скопированные в отдельную папку без изменения `artifacts`:

| Файл 0.1.0 | SHA-256 |
|---|---|
| `SSHExplorer.exe` | `433CBB4167AD9BB72DE8374DA69CF156955716BD27C402EF858A46270444F935` |
| `SSHExplorer.dll` | `769ACEC50C113E5DE5236F08400809EE9696078C7B50DEF68C496F1DC3C09A62` |

Минимальная детерминированная проба: отдельный пустой store → один сохранённый offline-профиль → настоящий `MainWindow` и фактический WPF layout его содержимого → выбор строки реальной `DataGrid`. Окно в этой пробе не показывалось, мышь и фокус рабочего стола не использовались. Старый процесс воспроизводимо завершился `0xC00000FD`; в стеке многократно повторились `HomeViewModel.Rebuild`, `MainWindow.RefreshHome` и обработчик `MainWindow.<.ctor>…SelectionChanged`.

Это доказывает причину в тех же опубликованных DLL. Это **компонентная WPF-проба**, а не утверждение о завершённом живом ручном вводе через опубликованный EXE.

## Дополнительно исправленная атомарность

В старом сценарии форма сначала закрывалась, затем `MainWindow` менял `Profiles` в памяти и только после этого вызывал запись настроек. Отказ записи оставлял частичную локальную запись и терял введённую форму. Это отдельный дефект, а не причина переполнения стека.

Новый `ProfileDialog` остаётся открытым до завершения `ProfilePersistence` / `AppStore.SaveProfileAsync`:

1. Проверяет поля без сетевого подключения.
2. При выбранном сохранении секрета шифрует его DPAPI CurrentUser и записывает под новым случайным именем.
3. Атомарно заменяет `settings.json`, содержащий ссылку на защищённый секрет. Это точка commit.
4. Только после commit меняет коллекцию профилей и ссылку на секрет в памяти.
5. При отказе до commit удаляет только собственный staged-файл; исходный профиль, JSON и прежний секрет остаются действующими.

Удаление профиля также меняет память после успешной записи. Старые профили и DPAPI-файлы, привязанные непосредственно к ID профиля, читаются и переходят на новую ссылку при обычном редактировании. При отключении сохранения защищённый секрет удаляется и больше не читается. Если удаление **прежней зашифрованной копии после успешного commit** запрещено файловой системой, пользователь получает отдельное предупреждение; это не выдается за откат уже сохранённого профиля. Ни JSON, ни журналы не содержат открытого пароля или passphrase.

## Новая форма

- Компактные поля имени, адреса с коротким полем порта, пользователя и способа входа.
- Адрес может быть недоступным offline DNS-именем, IPv4, IPv6, IPv6 в квадратных скобках или IDN. Сохранение не выполняет connect/DNS-проверку.
- Блок приватного ключа полностью свернут в режиме пароля. Сам ключ не копируется в настройки; passphrase поддерживается отдельно.
- Есть настоящий `PasswordBox` и явный opt-in сохранения. Без сохранения пароль можно оставить пустым и ввести при входе.
- Стартовая папка и timeout — в `Expander`. Порт проверяется в диапазоне 1–65535, timeout — 3–120 секунд; некорректные значения не подменяются clamp.
- Ошибки полей и ожидаемые отказы хранения показаны inline, без закрытия и потери ввода.
- Сохранение защищено от повторного нажатия. Пока commit выполняется, закрытие формы блокируется до известного результата.
- Кнопки закреплены внизу, содержимое прокручивается при недостатке высоты; назначены owner, начальный фокус, default/cancel действия и accessibility names.

### Уточнение синхронизации CI-теста

В GitHub Actions run `41632389182` на checkpoint `06458bc` модальный тест успел подтвердить сохранение ввода при неверном порте, затем повторно выполнил ту же проверку после исправления порта, пока асинхронная запись ещё продолжалась. Проверка закономерно увидела уже снятую ошибку. На быстром локальном диске окно закрывалось до следующего timer tick, поэтому исходный локальный прогон эту гонку теста не выявил.

Это **дефект синхронизации тестового сценария**, не новая регрессия формы. Проверка ввода сохранена; сценарий теперь явно разделён на фазы «неверное поле», «проверить сохранённый ввод и исправить», «дождаться commit/закрытия». Сценарий отказа записи использует такие же фазы, а лимит ожидания измеряется реальным временем, не числом dispatcher ticks. После пользовательского указания не показывать окна на рабочем хосте повторный modal-прогон переносится в GitHub Actions; локально выполняются Release build и `--no-windows`. Прежние 65/65 выше относятся к указанному локальному прогону, а не являются результатом нового CI.

После исправления синхронизации выполнены **Release build: 0 warnings/errors** и **54/54 `--no-windows`: PASS**, [лог](test-results/profiles-v02-headless.log). В этом повторном прогоне не было ни одного `Show()` и не использовался пользовательский рабочий стол. Результат следующего модального CI-прогона пока ожидается.

## Воспроизведение тестов

```powershell
# Полный modal STA набор. Требует согласованного окна без другого UI-оператора.
dotnet run --project tests/SSHExplorer.ProfileTests -c Release
# Нет ни одного Show(): модель, реальные отказы хранения, layout/selection настоящей DataGrid.
dotnet run --project tests/SSHExplorer.ProfileTests -c Release -- --no-windows
# Дополнительный профиль→DPAPI→реальный SSH/SFTP на изолированном проверенном стенде.
dotnet run --project tests/SSHExplorer.ProfileTests -c Release -- --no-windows --ssh-fixture .tools/iteration2/linux-a/integration.json
```

Конфиг стенда и секреты находятся только в ignored `.tools`; при отсутствии стенда сетевой сценарий не запускается. Источником независимого host fingerprint является подготовка disposable fixture, не автоматически принятый ключ из проверяемого соединения.

Для воспроизведения старого crash в отдельной копии 0.1.0: собрать `SSHExplorer.ProfileTests` с `-p:ProfileBaselineAssemblyDir=<каталог_старой_поставки>` и отдельным `OutDir`, затем выполнить тестовый EXE с `--selection-only`. Ожидаемый старый результат — `0xC00000FD`. Не заменять DLL работающего приложения и не выполнять этот fatal-процесс внутри основного тестового runner.
