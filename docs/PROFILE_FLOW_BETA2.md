# Профили и парольный вход beta.2

`Сохранить` и `Сохранить и подключиться` имеют отдельные результаты. При подключении точное содержимое общего поля пароля передаётся в памяти. Пробелы, кавычки, Unicode и пустая парольная фраза ключа не обрезаются. Временное отображение пароля меняет только представление поля. Неотредактированное пустое поле обычного пароля означает, что нужен стандартный запрос учётных данных.

Если пользователь включил сохранение, `Сохранить и подключиться` сначала записывает профиль без нового секрета. После успешного подключения вызывается `SaveAuthenticatedSecretAsync`. Метод проверяет, что профиль существует, сохранение ещё включено, адрес, порт, имя пользователя, способ входа и путь ключа соответствуют успешной попытке. Поздний ответ от удалённого или изменённого профиля не записывает секрет. При отказе атомарной записи прежняя защищённая копия остаётся действующей. Отдельное `Сохранить` явно сообщает, что запись введённого секрета происходит без сетевой проверки.

`ProfileSubmission` не включает секрет в `ToString()`. Диагностика сохранения пишет GUID редактора, этап, результат и очищенные сведения об исключении; пароль и поля профиля в неё не включаются. Настройки показывают версию и commit сборки. Кнопка копирования диагностики копирует только путь к каталогу журналов.

Запросы Credentials, Trust и Interactive принимают владельца и токен отмены. Общий `ModalRunner` закрывает показанный запрос при отмене с другого потока и закрытии владельца. Уже отменённый запрос не создаёт окно. Сериализация и проверка актуальности очереди конкретной попытки принадлежат `ConnectionInteraction`; этот компонент не создаёт собственную очередь диалогов.

## Подтверждённые проверки

Прежние [85/85](test-results/beta2-profiles-headless.log) и [92/92](test-results/beta2-profiles-published-baseline.log) сохраняются как исторические журналы. **Утверждение, что эти прогоны гарантированно выполнялись без окон и без обращения к обычному хранилищу, отозвано.** WPF ставит `Application.OnStartup` в Dispatcher уже из конструктора, даже без `Application.Run`. Старый runner создавал обычный `new App()`; последующий pump мог запустить настоящий startup, создать лишний MainWindow и заменить назначенный тестом store. Этот дефект изоляции обнаружен по лишнему MainWindow в CI. Исторические результаты не служат доказательством чистого headless-прогона.

Исправленный runner использует только внутренний `new App(startDesktop:false)`. Он явно обрабатывает queued startup до создания первого Window и проверяет наблюдение callback, нулевой счётчик desktop startup, неизменность назначенного изолированного store и отсутствие окон. В конце headless-набора проверяются нулевые desktop startups, отсутствие видимых окон и native HWND. Обычный публичный конструктор приложения и пользовательские команды не меняют режим работы; внутренний режим теста подавляет только автоматический production startup.

После проверки защитного кода выполнены свежая Release-сборка в `.tools/profile-beta2-isolated` (**0 warnings / 0 errors**) и новый изолированный `--no-windows --baseline-core` прогон: **94/94 PASS**. Это 92 прежние проверки, повторённые с исправленной изоляцией, и две проверки startup/final HWND. [Новый журнал](test-results/beta2-profiles-isolated-headless.log) содержит начальные и конечные `SAFETY` записи: queued callback обработан, desktop startup = 0, исходный изолированный store не заменён, visible windows = 0 и native HWND = 0. [Метаданные и SHA256](test-results/beta2-profiles-isolated-headless.meta.json). Только этот новый прогон подтверждает отсутствие окон в профильном наборе.

В набор входят реальные Windows DPAPI, реальные ошибки доступа и sharing violation в изолированном каталоге, транзакции секрета после входа, сохранение прежнего корректного секрета, пустая passphrase, чтение клона schema1, настоящие непоказанные WPF-контролы и обработчики изменения текста. Искусственно вызванный Loaded в проверке позднего чтения — компонентная проверка порядка обработки, не доказательство живого окна.

Клон beta.1 создаётся из отдельного schema1 fixture store в `.tools`, включая настройки, доверенный ключ и DPAPI reference. Исходные fixture bytes остаются неизменными. Это проверка совместимости формата; пользовательское хранилище не читается и не меняется.

Дополнительный `--no-windows --baseline-core <опубликованный-beta.1>/SSHExplorer.Core.dll` проверяет точную библиотеку опубликованной beta.1. Счётчики assertions не означают столько же пользовательских маршрутов. В отдельный collectible AssemblyLoadContext загружается точный Core из portable beta.1:

* InformationalVersion: `0.2.0-beta.1+eda137a734e8fc259eb97fca300b2072d11232a8`.
* SHA256 Core: `d9da19f09a2a6277930fc9d3c46aa6b4444393a83b40331c971b16a298693fca`.

Старые реальные API `SaveProfileAsync`, `SaveAsync` и `HostTrustStore.VerifyAsync` создали отдельный fixture store, включая DPAPI secret reference, настройки, bookmark и сохранённый host key. Загрузчик не загружал старый App, не создавал его окна и не запускал старый EXE. Beta.2 прочитала копию store, отредактировала профиль и повторно прочитала его с теми же ID и секретом. Подтверждены неизменные SHA256 исходных fixture файлов и всех DLL рядом с опубликованным Core. Старые опубликованные файлы не перезаписывались. Этот дополнительный тест необязателен в CI, поскольку baseline DLL не входит в репозиторий.

Дополнительно закрыт обнаруженный при анализе путь: удаление файла сохранённого секрета после открытия формы раньше могло вывести ожидаемую `InvalidOperationException` из асинхронного обработчика. Теперь ошибка показывается внутри формы, ввод сохраняется и повторное сохранение с новым значением возможно. Это отдельная регрессия с тестом, **не установленная причина пользовательского сообщения о падении**.

## Выполненные сценарии CI

В [успешном CI 41646603882](https://github.com/Jetvac/ssh-explorer/actions/runs/41646603882), commit `ab019761db7cb2d0ae401dcebb1c3ca2ec9cb34d`, полный профильный набор завершился **110 STA assertions PASS**. В него входят настоящие Credentials/Trust/Interactive/Profile диалоги, отмена с worker-потока, точный владелец, закрытие владельца и отсутствие оставшихся окон. [Выдержка component/STA журнала](test-results/beta2-ci-ab01976-components.log). Этот набор использует внутренний `App(startDesktop:false)`, подавляющий только автоматический startup; окна и команды сценария создаются явно. Оконные сценарии на рабочем хосте не повторялись. Без `CI=true` runner требует `--no-windows`.

Обычный сетевой маршрут использует общий `scripts/testing/auth_fixture.py`, а не внедрённые `suppliedCredentials` или `trustOverride`. Изолированный fixture генерирует собственный ключ и независимо вычисленный отпечаток, точный пароль с Unicode и пробелами, реальный SFTP каталог `README.txt` и пустую папку. CI меняет свойства настоящих контролов WPF и вызывает настоящие события кнопок:

1. MainWindow «Добавить сервер» → ProfileDialog PasswordBox → «Сохранить и подключиться».
2. Настоящий TrustDialog сравнивается с независимо записанным отпечатком fixture; кнопка доверия сохраняет ключ.
3. Проверяется отсутствие записи секрета до входа, Connected, фактическая навигация SFTP и README в таблице.
4. После записи DPAPI запускается новый процесс **тестового STA runner**. Он открывает тот же изолированный store и нажимает обычную кнопку «Подключиться», проверяя вход без нового Credentials/Trust окна.

Этот маршрут **прошёл в том же CI**: [ordinary STA + network журнал](test-results/beta2-ci-ab01976-ordinary-sta.log) содержит 8 parent assertions, включая startup guard и успешное завершение нового тестового процесса. Перед его запуском подтверждены настоящее событие Closed и удаление первого MainWindow из коллекции приложения. Проверка дочернего процесса подтверждена exit/summary assertion родителя; отдельный stdout дочернего процесса в загруженном artifact не сохранён, поэтому ему не приписывается отдельный числовой итог.

Отдельный probe запустил **собранный portable EXE** с новым изолированным settings-каталогом и штатно закрыл его: [PASS, exit 0](test-results/beta2-ci-ab01976-portable-startup.json), own HWND наблюдался, forced termination отсутствует. В этом probe пароль не вводился. [Полный отчёт об уровнях CI](CI_BETA2.md) разделяет эти доказательства.

```powershell
# Только непоказанные проверки на рабочем хосте.
.tools/profile-beta2-isolated/SSHExplorer.ProfileTests.exe --no-windows
# Дополнительная Core-only совместимость с точной опубликованной beta.1.
.tools/profile-beta2-isolated/SSHExplorer.ProfileTests.exe --no-windows --baseline-core <published-beta.1>/SSHExplorer.Core.dll
# Только в CI после запуска общего headless fixture.
SSHExplorer.ProfileTests.exe --ordinary-only --ordinary-fixture <ignored-fixture-directory>/fixture.json
```

Тестовый STA процесс не равнозначен опубликованному EXE; присваивание свойств контролам не равно физическому вводу. Этот CI не проверял скачанный опубликованный ZIP, физический парольный ввод, DPI/High Contrast или чистую Windows. Отдельная живая приёмка отражается в ACCEPTANCE/UI_PARITY. Падение актуальной beta.1 при парольном входе пока не воспроизведено; успешный CI не объявляется доказательством устранения неизвестного падения.
