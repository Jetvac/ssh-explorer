# Размер поставки и быстродействие

Документ разделяет измеренное и оценённое. Источники чисел лежат в [docs/perf](perf). «MB» означает 10⁶ байт, «MiB» — 2²⁰ байт.

## 1. Состав опубликованной beta.5

Измерено скриптом `scripts/Measure-Package.ps1` (категории по путям) на распакованном `SSHExplorer-0.2.0-beta.5-win-x64.zip`: [package-beta5.json](perf/package-beta5.json).

| Компонент | Файлов | Байт | Доля |
|---|---:|---:|---:|
| WebView2 Fixed Runtime (только для терминала xterm.js) | 257 | 706 209 931 | 81,5 % |
| .NET runtime (Microsoft.NETCore.App) | 185 | 80 337 880 | 9,3 % |
| .NET WindowsDesktop (WPF) runtime | 53 | 57 096 432 | 6,6 % |
| Сателлитные ресурсы WPF/WinForms (13 языков) | 156 | 8 688 328 | 1,0 % |
| Сторонние библиотеки (SSH.NET, BouncyCastle, WebView2 SDK…) | 13 | 7 908 782 | 0,9 % |
| Документация разработчика (`docs/`, отчёты, снимки) | 162 | 3 388 936 | 0,4 % |
| Собственный код SSH Explorer | 9 | 1 364 900 | 0,2 % |
| Терминал (xterm.js) | 7 | 580 074 | 0,1 % |
| Лицензии и уведомления | 19 | 387 333 | <0,1 % |
| Метаданные поставки | 2 | 90 951 | <0,1 % |
| **Итого распаковано** | **863** | **866 053 547** (≈ 826 MiB) | |
| ZIP | 1 | 392 175 022 (≈ 392,18 MB, 374,01 MiB) | |

`SSHExplorer.exe` — 162 816 байт: это apphost, а не приложение целиком. Размер ZIP не равен ни размеру EXE, ни расходу памяти.

После первого запуска появляются `%LOCALAPPDATA%\SSHExplorer\WebView2` (профиль терминального движка), `TransferCache` (только при системном копировании файлов), `Logs` (до 2 × ~1 МБ) и настройки. Их размер на Windows в этой итерации не измерен: CI-прогон beta.6 не выполнялся.

## 2. Что изменено в beta.6

- `Build-Release.ps1` кладёт в пользовательский комплект только README, CHANGELOG, THIRD-PARTY-NOTICES и `licenses/`. Отчёты разработчика, исторические снимки и `docs/` (162 файла, 3,39 МБ) остаются в репозитории и архиве исходников. Это −19 % файлов и только −0,4 % объёма.
- `SatelliteResourceLanguages=ru` оставляет русские ресурсы WPF вместо 13 языков. По beta.5 это около 7,9 МБ распакованных данных из 8,7 МБ.
- `PublishReferencesDocumentationFiles=false` убирает IntelliSense XML пакета WebView2 (0,8 МБ).
- Оценка экономии ≈ 12 МБ распакованных данных, ≈ 1,4 % объёма. Число не измерено на собранной beta.6, потому что CI не запускался. Главный объём по-прежнему занимает WebView2 Fixed Runtime.

## 3. Стоимость мониторинга (сервер), до и после

Причина медленного сбора — серверный shell-скрипт, а не WPF. Скрипт beta.5 запускал несколько вспомогательных процессов на каждый PID и собирал процессы даже для страницы «Производительность». Измерение: `--collector-benchmark` против того же `/proc` (369 процессов, 2 vCPU, dev-контейнер Linux, медиана), [collector-benchmark-dev-container.json](perf/collector-benchmark-dev-container.json).

| Запрос | Медиана, мс | fork | Ответ, байт |
|---|---:|---:|---:|
| beta.5, полный сбор (при любой странице) | 3 305,7 | 5 594 | 1 052 162 |
| beta.6, только система (графики, «Сервер») | 22,1 | 35 | 7 458 |
| beta.6, процессы (кэш cmdline прогрет) | 107,8 | 38 | 296 337 |
| beta.6, первый сбор процессов (ограничен 512 cmdline) | 999,4 | 1 145 | 315 205 |
| beta.6, сведения «Сервер» (однократно) | 30,9 | 49 | 8 200 |

Результат: в 150 раз быстрее для системных метрик, в 30 раз — для постоянного опроса процессов. Сетевую задержку SSH это не включает. На Windows-стенде с реальным сервером до/после не измерено. Linux-задание CI повторяет этот benchmark против тега v0.2.0-beta.5, но ещё не запускалось.

## 4. Варианты уменьшения поставки

Размеры вариантов B и C — **оценки**. Они получены переупаковкой подмножеств опубликованного дерева beta.5 (`zip -9`), ни один вариант не собирался и не запускался: [package-variants-beta5.json](perf/package-variants-beta5.json).

| Вариант | Распаковано | ZIP | Память | Цена перехода |
|---|---:|---:|---|---|
| A. beta.6 как есть (WPF + .NET + WebView2 Fixed) | ≈ 854 МБ | ≈ 390 МБ | процесс WPF + процессы msedgewebview2 на терминал | — |
| B. WPF + системный Evergreen WebView2 | ≈ 149 МБ | ≈ 64 МБ | без изменений | правка `TerminalView` и `Build-Release.ps1`; проверка наличия runtime |
| C. WPF + нативный renderer терминала | ≈ 149 МБ | ≈ 64 МБ | без браузерных процессов | новый renderer: VT, Unicode, выделение, поиск, IME, доступность |
| D. Rust + Win32 (прототип) | единицы МБ (ожидание) | — | не измерено | переписать всё приложение |

**B.** Windows 11 поставляется с Evergreen WebView2, и это рекомендованная Microsoft модель распространения. Runtime обновляется сам, что полезно для безопасности. Риски: управляемые или LTSC-системы, где runtime удалён, и смена версии движка без нашего участия. Нужна явная проверка при открытии терминала с понятным сообщением. Отдельный «полный» комплект с Fixed Runtime можно сохранить для таких систем.

**C.** Убирает и размер, и браузерные процессы. Ядро VT, нужное для этого, уже написано и протестировано в Rust-прототипе (`prototypes/rust-explorer/core/src/terminal.rs`). Для C# его нужно перенести или подключить нативной DLL. Совместимость с TUI (mc, htop, vim), IME и экранными дикторами придётся проверять заново.

**D.** Rust-прототип проверяет трудные границы нативного стека (раздел 5). Но SSH Explorer — это не только окно. Перенос Explorer-OLE с virtual files, восьми представлений, редактирования с восстановлением, очереди передач, мониторинга, профилей с DPAPI и host keys — отдельный многоэтапный проект. Rust ничего не меняет в стоимости серверного сборщика (раздел 3).

**Не рассматриваются как способ уменьшения:**

- Single-file: меняет упаковку, но runtime остаётся внутри, а нативные библиотеки WPF распаковываются при запуске.
- Trimming и NativeAOT: для WPF официально не поддерживаются, к тому же сборка использует проверяемый reflection-адаптер SSH.NET.
- Tauri: на Windows это тоже WebView2, то есть вариант B с полным переписыванием.
- Framework-dependent сборка (около 10 МБ): требует установленного .NET Desktop Runtime. Это допустимо только как отдельно обозначенный облегчённый вариант, не как основной portable.

## 5. Rust-прототип: что проверено

Каталог [prototypes/rust-explorer](../prototypes/rust-explorer/README.md) изолирован, в выпуск не входит и не публикуется как замена.

- **Проверено в Linux dev-контейнере** ([rust-prototype-dev-container.json](perf/rust-prototype-dev-container.json)):
  - 21 тест ядра. 8 из них — против настоящего SSH-сервера (libssh2 + OpenSSL ↔ локальный paramiko): host key проверяется до любых учётных данных, при отказе или смене ключа нет попыток аутентификации, upload эксклюзивный, SFTP-список из 10 004 объектов строится за 299 мс, PTY с resize работает, поток exec проверен.
  - Разбор терминального потока: 75,7 МБ/с. Сортировка 100 000 строк по двум ключам: 173 мс.
  - Win32-приложение проходит type-check и clippy без предупреждений.
  - `.res` с иконкой и манифестом побайтно совпадает с выводом `llvm-rc`.
- **Не выполнено:**
  - сборка и запуск EXE на Windows;
  - размер, запуск и память;
  - кадр GDI;
  - клик заголовка через SendInput;
  - drop из Explorer;
  - live-тесты против OpenSSH.

  Всё это подготовлено в `.github/workflows/rust-prototype.yml`. Workflow не запускался, потому что push в GitHub из этой сессии заблокирован.

## 6. Решение

1. **Стек beta.6 сохраняется.** Исправления 11 замечаний сделаны в WPF. Стабильная версия не теряет DnD, редактирование, восстановление и совместимость.
2. **Следующий шаг по размеру — вариант B** с проверкой наличия runtime: ZIP уменьшается примерно в 6 раз без переписывания. Он меняет обещание «всё в комплекте», поэтому требует решения пользователя и отдельной записи в README. Без этого решения в beta.6 он не включён.
3. **Вариант C или D выбирается по измерениям прототипа на Windows.** Условия: Windows-задание `rust-prototype.yml` проходит и даёт размер EXE, время до первой отрисовки, память и время кадра. Если преимущество подтверждено, первый этап миграции — терминал (VT-ядро и renderer), потому что он устраняет WebView2 при любом дальнейшем выборе UI. Полный перенос на Rust начинается только с планом паритета функций и сохранением формата профилей, host keys и DPAPI-секретов.
