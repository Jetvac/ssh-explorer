# Продолжение разработки SSH Explorer: Блокнот, системные иконки и доводка Windows 11

Ты продолжаешь существующий проект SSH Explorer:
https://github.com/Jetvac/ssh-explorer

Работай как разработчик Windows desktop-приложения, инженер SSH/SFTP и специалист по интерфейсам Windows 11. Реализуй изменения, проверь результат, сохрани работу в GitHub и выпусти следующую beta. План и отчёт должны сопровождать выполненную работу.

## 1. Исходная точка и цель

Проверенная на момент подготовки задания база — v0.2.0-beta.4, коммит 1fb919fbf87ff0baa6ecf6fcca242a6b68e614fb. Перед изменениями проверь актуальные main, теги, рабочее дерево и инструкции проекта. Если уже появился более новый код, сохрани его и скорректируй задачи по фактическому состоянию. Чужие изменения не перезаписывай.

Последняя обратная связь пользователя:

> «Пусть продолжает работу, дорабатывает, например, редактирование текстовых файлов — до уровня Блокнота Windows либо открывает в Блокноте Windows. Остальной функционал, иконки и т.д. Пока выглядит “нейроно” или просто примитивно в плане размеров и иконок».

Главные результаты этой итерации:

1. Законченный сценарий редактирования удалённого текста в настоящем Блокноте Windows с управляемым сохранением обратно на сервер.
2. Качественные значки файлов и папок, согласованные с установленной Windows.
3. Цельная геометрия интерфейса: вкладки, адрес, команды, дерево, таблицы, меню и диалоги.
4. Сохранение работающих SSH/SFTP, терминала, мониторинга и передач.

В beta.4 уже реализованы inline rename/create, исправление ошибочного адреса, рамка выделения с прокруткой, адаптивные панели, шаблоны полей, переполнение вкладок и настройки мониторинга. Сохрани эти результаты. Редактирование имени файла не является редактированием его содержимого.

В проверенной базе FileBrowserView.Open() открывает текст до 256 КиБ в read-only TextBox через UTF-8. FileSystemIcons.cs рисует собственные упрощённые значки. Это конкретные точки развития. Версию приложения и DPI последнего пользовательского скриншота нельзя достоверно установить по изображению.

Сохрани WPF/.NET и существующую архитектуру. Итоговая поставка по-прежнему запускается через EXE из полного portable-комплекта без отдельно устанавливаемых интерпретаторов. На управляемый Linux-сервер приложение ничего не устанавливает; работает через SSH/SFTP. Основное редактирование должно работать и с SFTP-only аккаунтом; необязательные возможности SSH exec не становятся скрытым условием.

## 2. Основной редактор — настоящий Блокнот Windows

Для этой итерации выбери разрешённый пользователем вариант с системным Блокнотом. Доведи связку целиком: удалённый файл → локальная рабочая копия → редактирование → подтверждённое сохранение на сервер.

Добавь понятную команду **«Редактировать в Блокноте»** для одного обычного текстового файла. Предусмотри настройку предпочитаемого установленного текстового редактора. Двойной щелчок по распознанному тексту должен открывать выбранный редактор; отдельная команда «Просмотр» сохраняет возможность открыть файл без редактирования. Изображения продолжают открываться в просмотрщике.

Поддержи типичные серверные документы: .txt, .log, .conf, .cfg, .ini, .json, .yaml, .yml, .toml, .xml, .md, .sh, .service, .env и текстовые файлы без расширения. Расширение — подсказка, а не единственная проверка содержимого.

Блокнот даёт пользователю обычное выделение, Undo/Redo, поиск, замену, переход к строке, перенос строк и масштаб. Не строй параллельно собственный клон редактора, если основной сценарий уже удовлетворяет запросу. Существующий встроенный просмотр можно сохранить, но не называй его полноценным редактором.

Запускай конкретный доверенный executable редактора с отдельным аргументом пути. Не используй cmd, PowerShell, склеивание shell-команд или открытие самого удалённого файла по произвольной Windows-ассоциации. Открытие .sh, .bat, .ps1 и других текстов для правки не должно выполнять их.

Разрешай системный Блокнот через корректный Windows-путь/механизм запуска, учитывая установленную реализацию. Если он отсутствует или запуск не удался, предложи выбрать установленный редактор либо сохранить локальную копию. Не устанавливай редактор автоматически и не нарушай работу остальных функций.

## 3. Рабочая копия и точность данных

Сделай явную модель RemoteEditSession, отделённую от визуального FileBrowserView. Она хранит серверную идентичность, исходный путь, разрешённую цель ссылки при её явном открытии, локальную копию, исходный content hash, метаданные и состояние синхронизации.

Идентичность включает профиль/endpoint/пользователя и проверенный SSH host key. Одноимённые файлы разных серверов и каталогов не должны пересекаться. Повторное открытие того же документа использует существующую рабочую копию; не создаёт две независимо отправляющие версии. Изменение профиля не должно перенаправлять незавершённую правку на другой сервер.

Храни рабочие копии в отдельном каталоге данных пользователя с уникальными идентификаторами и точным отображением локальный путь ↔ удалённый путь. Учти несовместимые с Windows имена, регистр, reserved names и длинные пути. Не восстанавливай удалённый путь из одного basename.

Скачивай и отправляй байты без промежуточного преобразования всего документа в UTF-8. Сохраняй BOM, кодировку, LF/CRLF, смешанные окончания и финальный перевод строки в том виде, который фактически записал редактор. Клиент не добавляет собственную нормализацию. Изменения формата, сделанные самим внешним редактором, нужно отличать от изменений, внесённых SSH Explorer. При обнаруженной смене кодировки/BOM или массовом преобразовании окончаний строк перед отправкой дай краткое подтверждение изменения формата, особенно для Linux-скриптов.

Для распознавания текста сначала учитывай BOM и UTF-16; отсутствие нулевого байта не является достаточным детектором текста. При декодировании для собственного просмотра используй строгую проверку и явный выбор кодировки, без молчаливой замены символов. Неизвестную legacy-кодировку не выдавай за уверенно распознанную.

Убери привязку редактирования к старому лимиту предпросмотра 256 КиБ. Проверь обычный сценарий хотя бы на текстах порядка 10 МиБ и длинных строках; установи обоснованный предел и понятный путь для более крупных файлов. Передачи и хеширование не блокируют UI, доступны отмена и прогресс.

Рабочие копии могут содержать конфигурации и секреты. Они не попадают в логи, Git, CI-артефакты или ZIP поставки. Содержимое не отправляется в сторонние сервисы. Очистка касается только собственных завершённых edit sessions по понятной политике хранения.

## 4. Понятное сохранение и жизненный цикл

Основной пользовательский маршрут:

- Пользователь открывает файл в Блокноте.
- Редактирует и сохраняет его обычным Ctrl+S.
- SSH Explorer обнаруживает новую сохранённую локальную версию и отправляет её по SFTP.
- После проверки результата показывает, какая версия подтверждённо сохранена на сервере.

При первом таком открытии кратко объясни: «Сохраняйте файл в редакторе — изменения будут отправлены на сервер». В SSH Explorer всегда можно увидеть сервер, полный удалённый путь и статус. Сделай компактный список редактируемых документов с действиями «Открыть редактор», «Проверить изменения», «Отправить сейчас», «Повторить», «Сохранить локальную копию», «Завершить редактирование». Действия доступны по состоянию.

Различай подготовку, открытую рабочую копию, ожидающие отправки изменения, отправку, подтверждённое сохранение, конфликт, ошибку, приостановку и неизвестный результат после обрыва. Не показывай успех только потому, что изменился локальный файл или завершилась очередь.

FileSystemWatcher является сигналом перечитать состояние. Обработай дубли событий, атомарную замену локального файла редактором, rename/delete/create, временную блокировку и переполнение watcher. Предусмотри сверку при возвращении в приложение и ручную проверку. Исчезновение рабочей копии не инициирует удаление или обнуление серверного файла. Сохраняй последний известный snapshot; пустую версию отправляй только после успешного чтения реально существующего сохранённого файла.

Перед отправкой получай устойчивый неизменяемый snapshot локальных байтов. Объединяй бурст событий, повторяй чтение при незавершённой записи. Для каждого документа сериализуй сохранения и отслеживай версии: старое сохранение не может затереть более новое. Совпадающий с последней подтверждённой версией content hash не вызывает новую отправку. Пустой сохранённый файл — допустимый результат, его нельзя объявлять ошибкой лишь по размеру.

Не связывай документ с временем жизни запущенного процесса. Блокнот может использовать вкладки и восстановление сессии. Закрытие окна или стартового процесса не означает, что текст записан в рабочий файл. Несохранённый буфер внешнего редактора SSH Explorer не видит; не обещай его синхронизацию или восстановление. Не читай внутренние базы и память Блокнота.

«Сохранить как» во внешнем редакторе в другом месте создаёт другую локальную копию. Она не должна автоматически подменять серверный документ. Предусмотри явное подключение выбранной копии к документу или «Сохранить на сервер как…», с проверкой назначения.

При закрытии серверной вкладки SSH-сессия закрывается. До закрытия предложи понятное решение для известных ожидающих отправки изменений: дождаться подтверждения, оставить локальную копию и отключиться либо отменить закрытие. Не держи скрытое SSH-подключение ради редактора.

При отмене, отключении и закрытии серверной вкладки не завершай процесс внешнего редактора и не закрывай его документы принудительно, включая открытые самим SSH Explorer. Рабочая копия и её отображение сохраняются, пока документ не завершён пользователем. После перезапуска предложи восстановить ожидающие документы; повторное подключение требует обычной проверки host key, сервера и текущей версии файла. Не отправляй старый черновик автоматически при старте приложения.

## 5. Сохранение на Linux без молчаливой потери данных

Выдели документное сохранение в проверяемый сервис. Переиспользуй надёжные транспортные примитивы, но проверь их контракт: нынешний Transfers.CommitRemote сравнивает преимущественно метаданные, чего недостаточно для защиты редактора от внешних изменений.

При открытии запоминай хеш исходных байтов и доступные метаданные. Перед заменой заново прочитай актуальное содержимое назначения и сравни с базовой версией. Изменение тех же байтов по длине с восстановленной mtime тоже должно обнаруживаться. Проверь тип объекта, путь и согласованную цель ссылки.

При конфликте сохрани локальную работу и предложи понятный выбор: посмотреть/получить серверную версию, сохранить свою рядом, продолжить правку либо явно заменить проверенную серверную версию. Отмена ничего не теряет. Повторное внешнее изменение снова требует разрешения конфликта; старое подтверждение не даёт бесконечного права перезаписи.

До финализации атомарно сохраняй локальную запись операции: идентичность документа, hash предыдущей серверной версии, hash отправляемого snapshot и его поколение. Рабочая копия и незавершённая операция должны пережить аварийный выход; восстановление не опирается только на память процесса.

Обычное сохранение:

1. Зафиксировать локальную версию и её hash.
2. Загрузить в собственный уникальный sibling temporary, с ограниченными правами во время записи.
3. Проверить полноту содержимого и необходимые метаданные.
4. Повторно проверить ожидаемую серверную версию непосредственно перед финализацией.
5. Выполнить поддерживаемую сервером замену.
6. Подтвердить результат чтением/проверкой назначения и только затем обновить baseline документа.

Исходный файл не обнуляется до завершения загрузки. Не используй delete+upload как обычную замену. Удаляй только точно принадлежащие этой операции временные объекты.

Обрыв после отправки финального rename может оставить неизвестный результат. При восстановлении сначала сравни назначение с исходной и отправляемой версиями; не выполняй слепой повтор. Если на сервере третья версия, сохрани локальный snapshot и покажи конфликт. Ошибка проверки после commit не разрешает автоматически затирать актуальный файл rollback-ом.

Сохраняй POSIX mode, включая executable bit. Owner/group проверяй и сохраняй в пределах прав пользователя; если требуемые значения восстановить нельзя, не заменяй оригинал молча, сохрани рабочую копию и предложи отдельное назначение. Замена через новый inode может менять дополнительные атрибуты и поведение hard links: не обещай сохранение ACL/xattr/hardlink-семантики без реализованной проверки. Для неподдерживаемого случая дай объяснение и сохранение отдельной копии либо явно согласованный режим; не применяй скрытое повышение прав.

Символическую ссылку открывай только с явным выбором работы с целью. Сохраняй документ в согласованную цель, не заменяй саму ссылку обычным файлом. Изменение цели во время правки — конфликт. FIFO, sockets и устройства не открываются как документы.

Документируй границы протокола: атомарный POSIX rename не является универсальным compare-and-swap по хешу; между проверкой и заменой остаётся окно гонки стороннего писателя. Fallback через backup не называй атомарным. Flush не равен подтверждённому физическому fsync. Не заявляй гарантий, которых реально нет.

## 6. Иконки, соответствующие Windows 11

Заменяй прежде всего упрощённые значки объектов из FileSystemIcons.cs. Командные глифы уже используют Segoe Fluent Icons; их нужно согласовать по ролям и оптическим размерам.

Для папок и обычных типов файлов используй системные иконки установленной Windows во время работы. Подходящий механизм — Windows Shell icon/image-list API с запросом по расширению и атрибутам, без скачивания удалённого файла. SHGetFileInfoW с SHGFI_USEFILEATTRIBUTES может быть частью реализации.

Требования к провайдеру:

- качественные варианты для таблицы, дерева, маленьких и крупных значков;
- размерный/DPI-aware кэш и корректная реакция на смену темы/окружения;
- фоновые Shell/COM-вызовы, корректное владение native handles;
- отсутствие зависания списка из 10 000 файлов на извлечении иконок;
- аккуратный fallback неизвестного типа и Linux special files;
- различимый overlay ссылки, без обязательного скачивания её цели;
- отсутствие выполнения удалённых файлов и запуска ассоциированных программ ради значка.

Не увеличивай маленький bitmap до огромного вида. Не размножай нынешнюю простую геометрию в разных цветах. Не используй emoji как набор объектных иконок. Не включай извлечённые Windows DLL/шрифты в поставку; обращайся к установленным системным ресурсам. Для включаемого fallback-набора сохрани лицензию.

Системные ассоциационные иконки могут отличаться между ПК — это нормальное свойство выбранного подхода, его нужно учитывать в тестах.

Для команд централизуй семантический каталог глифов и размерные роли. Разделяй размер изображения и область нажатия. Выравнивай оптический центр и вес, проверяй чёткость при дробном DPI. Основные размеры выбирай из рекомендуемых для Segoe Fluent Icons; не применяй один FontSize ко всем ролям.

## 7. Размеры и компоновка

Выбери один воспроизводимый Windows 11 Explorer-референс. Зафиксируй известные build, тему, DPI, масштаб текста, плотность и размер клиентской области. Сравни Windows → опубликованную beta.4 → новую сборку. Если масштаб исходного референса неизвестен, прямо отметь это и не выдавай пиксельные оценки за точные системные DIP.

Сначала доведи целиком экран «Файлы», затем перенеси общие решения на «Главную», мониторинг, терминал, формы и панель редактируемых документов.

Проверь взаимные пропорции вкладок, навигационных кнопок, адресной строки, поиска, command bar, дерева, заголовков таблицы, строк и status bar. Настрой роли размеров/интервалов/радиусов в общих ресурсах. Разные роли могут иметь разные значения; проблема решается согласованной композицией.

Стандартная плотность должна выглядеть привычно рядом с Проводником. Компактный режим, если реализуешь его, должен менять высоты и интервалы согласованно. Увеличенный системный текст не обрезается. Смена плотности и темы сохраняет выделение, скролл, ширины колонок, текущий путь и активное редактирование имени.

Конкретные задачи текущей оболочки:

- При отсутствии переполнения вкладок скрывай области стрелок прокрутки. Сейчас они занимают место даже при двух вкладках. При переполнении обе области имеют стабильную геометрию, крайние направления правильно отключаются.
- Помести «+» у фактического конца полосы вкладок; служебные действия размести отдельно. Сохрани доступ ко всем вкладкам, область перетаскивания окна, native caption и корректный hit testing.
- Значок кнопки «Просмотреть» связывай с активным режимом. В меню beta.4 уже есть восемь разных глифов, а сама кнопка пока всегда показывает сетку.
- Проверь базовые линии подписей, отступы между иконкой и текстом, размеры меню, высоту адреса и поиска, границы и состояния выделения.
- Сохрани визуальное различие текущего раздела, выбранной папки, выбранного файла, клавиатурного фокуса и drop target.

В папке на пользовательском скриншоте один файл. Свободное пространство списка естественно. Не заполняй его декоративными карточками, подсказками или огромными элементами ради плотности картинки.

## 8. Поведение и анимации

Используй существующие UiMotion и реальные component templates. Доведи normal/hover/pressed/selected/inactive/focus/disabled/loading/error, в том числе после асинхронного обновления.

Меню открывается у источника, закрывается ожидаемым действием и возвращает фокус. Контекст выбранной группы не теряется. Ошибки остаются рядом с действием, которое их вызвало. Состояния редактирования текста отражаются спокойно, без модального окна на каждое успешное Ctrl+S.

Переходы должны быть короткими и прерываемыми; быстрые действия не накапливают анимации и не сдвигают область нажатия. Сохрани поддержку отключённых системных анимаций и High Contrast. По статичному PNG нельзя доказать плавность: фиксируй отдельно, какие переходы действительно проверены.

Проверь после визуальных изменений все восемь файловых видов, sorting, Back/Forward/Up, editable path, inline rename, multi-selection, context menus, previews, clipboard и drag/drop. Не оставляй декоративных кнопок без рабочего действия.

## 9. Проверка результата

Сохрани существующие обязательные CI-проверки. Добавь проверки новых рисков, без бессмысленного повторения уже закрытого большого тестового марафона.

Для редактора нужны:

1. Реальный SFTP round-trip .sh/.conf/.txt, пустого файла, Unicode и текста порядка 10 МиБ; контроль байтов и mode.
2. UTF-8 с/без BOM, UTF-16, LF/CRLF и финальный перевод строки. Для внешнего редактора отдельно отличай поведение transport bridge от поведения установленного Notepad.
3. Несколько быстрых локальных сохранений, замену файла через rename, дубли/пропуск watcher-событий и ручную сверку.
4. Изменение удалённого файла вторым клиентом, включая ту же длину и mtime; повторный конфликт после решения.
5. Обрыв до и после финализации, permission denied, нехватку места, отмену и сохранность локальной копии.
6. Два сервера с одинаковыми именами файлов; повторное открытие документа; закрытие сессии; восстановление pending-состояния после перезапуска.
7. Явную работу с symlink и отказ special files; отсутствие выполнения .sh.
8. Настоящую связку с установленным Блокнотом в разрешённой Windows-среде, если он там доступен.

Тестовый launcher или запись файла тестом подтверждают только соответствующие компоненты. Они не доказывают, что пользователь успешно отредактировал файл в реальном Блокноте. Внешний редактор не включается в состав нашего EXE и не должен подменяться фиктивным окном в отчёте.

Для визуальной приёмки используй сцену с папками, .sh/.conf/.json, текстами, архивами, фотографиями, неизвестным расширением, ссылками, длинными именами и выбранной группой. Нужны реальные кадры таблицы, малых/крупных значков, меню, двух и многих вкладок, узкого окна, формы и состояний редактируемого документа.

Для сравнения зафиксируй actual client size, DPI, тему, размер текста, культуру и состояние. Проверяй Light/Dark, увеличенный текст и доступную DPI/HC-матрицу. Не выдавай программное увеличение шрифта за изменение системного DPI.

В действующей приёмке beta.4 сохранён запрет Computer Use и host HWND. Не переноси старое временное разрешение beta.2 на новую работу. Продолжай код, headless-проверки и оконные проверки в разрешённом Windows CI. Непроверенные физические действия, Explorer DnD, native DWM/Snap, motion video и чистую Windows оставляй с точным статусом и воспроизводимыми шагами.

Причину прежнего пользовательского парольного вылета не объявляй установленной. При новом воспроизведении это вновь первый приоритет. Сохрани текущие auth/host-key/secret-регрессии.

## 10. GitHub, документация и выпуск

Делай осмысленные коммиты по завершённым изменениям и отправляй их в существующий репозиторий. Не откладывай всю работу в незакоммиченный итог. Не переписывай историю без необходимости.

Обнови README, CHANGELOG, ACCEPTANCE, UI_PARITY и документ редактирования файлов. Опиши обычный маршрут с Блокнотом, момент отправки, статусы, конфликты, отключение и восстановление. Отдельно зафиксируй ограничения метаданных/гонок и внешний Save As. Убери устаревшие названия beta.2 из примеров артефактов README.

Выпусти следующий свободный prerelease, например 0.2.0-beta.5, если номер ещё свободен. Приложи portable ZIP, исходники, checksums и реальные визуальные материалы. EXE, tag, commit, CI, screenshots и release notes должны относиться к одной проверенной версии.

Повторно проверь опубликованный артефакт и соответствие версии/хешей. Не распространяй локальные документы редактирования, секреты и тестовые профили.

В итоговом отчёте сначала покажи, что пользователь теперь может сделать: открыть текст в Блокноте, сохранить его на сервер, увидеть результат и восстановить работу при ошибке. Затем покажи визуальные изменения рядом с эталоном, ссылки на commit/CI/release и честные оставшиеся ограничения.

**Интерфейс принимает пользователь. Успешная сборка и рост числа assertions сами по себе не означают визуальную готовность.**
